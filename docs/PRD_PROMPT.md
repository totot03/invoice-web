# PRD 작성 메타 프롬프트 — Notion 연동 견적서 웹 뷰어 & PDF 다운로드

> 이 문서는 PRD(Product Requirements Document) 그 자체가 아니라, **PRD를 생성하기 위해 AI에게 전달할 프롬프트**입니다.
> 아래 "메타 프롬프트 본문"을 통째로 복사해 Claude(또는 다른 LLM)에게 전달하면, `docs/PRD.md`에 저장할 수 있는 완성된 PRD 마크다운 문서가 산출물로 나옵니다.

## 문서 정보

| 항목 | 내용 |
|---|---|
| 버전 | v1.0 |
| 작성일 | 2026-08-12 |
| 대상 프로젝트 | `invoice-web` (Next.js 16 App Router 스타터킷) |
| 목적 기능 | Notion에 입력한 견적서를 클라이언트 웹에서 열람 + PDF 다운로드 (MVP) |
| 산출물 저장 위치(권장) | `docs/PRD.md` |

## 사용법

1. 아래 "메타 프롬프트 본문" 코드 블록 전체를 복사한다.
2. 새 대화(또는 이 프로젝트가 로드된 Claude Code 세션)에 붙여넣는다.
3. AI가 생성한 PRD 마크다운을 검토한 뒤 `docs/PRD.md`로 저장한다.
4. `<open_questions>`에 나열된 항목은 실제 의사결정권자(기획자/PM)가 채운 뒤 PRD를 확정한다.
5. 요구사항이 바뀌면 `<context>`, `<constraints>` 블록만 수정해서 재사용한다 — 나머지 구조는 그대로 둬도 된다.

## 프로젝트 현황
- 프로젝트명: invoice-web (원래는 범용 Next.js 스타터킷, 이번 기능으로 실제 제품화 시작)
- 프레임워크: Next.js 16 (App Router, React Server Components 규칙 엄격 적용)
  - 주의: 이 Next.js 16은 학습 데이터의 구버전과 컨벤션이 다르다. 미들웨어는 `middleware.ts`가 아니라 `proxy.ts` 파일 컨벤션을 사용한다. 에러 바운더리 콜백은 `unstable_retry()`를 사용한다(구버전의 `reset` 아님).
- 언어/스타일: TypeScript strict, ES2017 target, `@/*` 경로 별칭
- 라우트 구조: 라우트 그룹 3개 존재 — `(marketing)`, `(auth)`, `(dashboard)`. 신규 기능을 위해 라우트 그룹을 추가하거나 기존 그룹 하위에 배치하는 방안을 모두 검토할 것.
- UI: Tailwind CSS v4(PostCSS 플러그인 방식, `@theme` 디렉티브 사용, 별도 tailwind.config 없음), shadcn/ui(Radix Nova 스타일, `components.json` 기준 `@/components/ui`에 위치), lucide-react 아이콘
- 폼: react-hook-form + Zod, 한국어 에러 메시지 (`lib/validations/`에 스키마 위치, 예: `lib/validations/auth.ts`)
- 알림: Sonner 토스트 (`Toaster`가 루트 레이아웃에 이미 마운트됨)
- 인증 현황: `app/(auth)/login/page.tsx`에 데모 로그인만 하드코딩되어 있음(`demo@example.com` / `demo123456`). 실제 백엔드 인증/세션/DB는 아직 없음.
- 컴포넌트 위치 컨벤션: `components/layouts/`(페이지 레이아웃 래퍼), `components/patterns/`(재사용 패턴, 예: `empty-state`, `page-header`, `stat-card`)
- 아직 없는 것: Notion API 연동 코드, 데이터베이스/ORM, PDF 생성 라이브러리, 파일 저장소, 이메일/링크 발송 인프라

## 신규 기능 요구사항 (사용자 원문 요약)
"Notion을 이용해서 입력한 견적서 내용을 클라이언트가 웹으로 확인하고, PDF로 다운로드할 수 있는 MVP."

이를 3개 계층으로 분해:
1. **입력 계층(내부용)**: 견적서 작성자가 Notion 데이터베이스에 견적서 항목(고객명, 품목, 단가, 수량, 합계, 유효기간 등)을 입력한다. Notion이 곧 CMS/DB 역할을 한다.
2. **열람 계층(외부 클라이언트용)**: 클라이언트가 별도 로그인 없이(또는 최소한의 인증으로) 공유된 웹 링크를 통해 자신의 견적서를 조회한다.
3. **출력 계층**: 클라이언트가 웹에서 본 견적서를 PDF로 다운로드한다. 회사 브랜딩(로고, 서식)이 포함되어야 한다.
</context>

<task>
아래 목차를 모두 채운 완전한 PRD를 한국어 마크다운으로 작성하라. 각 섹션은 실행 가능한 수준(개발자가 바로 티켓을 쪼갤 수 있는 구체성)으로 작성한다.

1. **문서 정보** — 버전, 작성일, 작성자(미정 시 "TBD"), 상태(Draft)
2. **배경 및 문제 정의** — 왜 이 기능이 필요한가(기존 견적서 발송 방식의 문제), 이 제품이 해결하는 핵심 pain point
3. **목표 및 성공 지표** — 정성적 목표 + 측정 가능한 KPI(예: 견적서 열람율, PDF 다운로드 전환율, 견적서 발송~확인까지 소요 시간)
4. **사용자 페르소나 및 유스케이스**
   - 내부 사용자(견적서 작성자): Notion에서 어떻게 작업하는가
   - 외부 사용자(클라이언트): 링크를 받아 어떻게 확인/다운로드하는가
5. **사용자 플로우** — 텍스트 기반 순서도 또는 Mermaid 다이어그램으로 "Notion 입력 → 동기화 → 링크 생성/발송 → 클라이언트 열람 → PDF 다운로드" 전 과정을 표현
6. **기능 요구사항 (MoSCoW로 우선순위화: Must/Should/Could/Won't)**
   - F1. Notion 연동: 데이터를 어떻게 가져올 것인가(Notion API 공식 연동 방식, Integration Token, Database ID 기준 조회). 동기화 방식 후보(Webhook 실시간 vs 주기적 Polling vs 수동 Sync 버튼)를 비교하고 MVP 권장안을 명시
   - F2. 견적서 상세 웹 페이지: 라우팅 설계 제안(예: `/estimates/[token]` 형태의 추측 불가능한 공개 링크), 필요한 표시 항목, 반응형/다크모드 대응 여부
   - F3. PDF 다운로드: 생성 방식 후보(브라우저 인쇄 API, 클라이언트 사이드 라이브러리 예: `@react-pdf/renderer`, 서버사이드 헤드리스 브라우저 예: Puppeteer/Playwright) 비교표 작성 후 MVP 권장안 제시(전략: 팀 규모/인프라 제약 고려)
   - F4. (선택) 접근 제어: 링크 만료, 조회 로그, 워터마크 등 보안 고려사항
7. **비기능 요구사항** — 성능(Notion API Rate Limit 대응), 보안(링크 추측 방지, 민감정보 노출 범위), 접근성(WCAG 기본 수준), 브라우저 호환성
8. **기술 아키텍처 제안** — 기존 스택(Next.js 16 App Router, TypeScript, Tailwind v4, shadcn/ui)과의 정합성을 유지하는 구조 제안. 신규로 추가될 의존성 후보 목록과 각각의 트레이드오프. RSC/Client Component 경계 제안(Notion API 호출은 서버에서, PDF 트리거 버튼은 클라이언트에서 등). 라우트 그룹 배치안(기존 3개 그룹 중 어디에 넣을지 혹은 신규 그룹 `(client)` 신설 여부)
9. **MVP 범위 정의** — In Scope 항목과 Out of Scope 항목을 명확히 분리한 표. (Out of Scope 예시로 고려: 다국어, 결제 연동, 이메일 자동 발송, 전자서명, 다중 워크스페이스)
10. **마일스톤 및 일정(안)** — 주 단위 스프린트 배분 제안(예: 1주차 Notion 연동 PoC, 2주차 웹 뷰어, 3주차 PDF, 4주차 QA/배포)
11. **리스크 및 대응 방안** — Notion API 제약(Rate Limit, 스키마 변경 시 파싱 깨짐), PDF 렌더링 품질 이슈, 링크 유출 리스크 등
12. **Open Questions** — 이 프롬프트만으로 확정할 수 없어 의사결정이 필요한 질문 목록(예: 클라이언트 인증 수준을 링크만으로 할지 이메일 인증을 추가할지, Notion 워크스페이스가 이미 존재하는지, 브랜딩 가이드가 있는지)
13. **부록** — Notion 데이터베이스 스키마 초안(속성명, 타입 제안), 용어집
</task>

- 특정 라이브러리를 권장할 때는 최소 2개 이상의 대안과 비교한 뒤 선택 근거를 1~2문장으로 남긴다(단정적 추천 금지, 트레이드오프 명시).

</constraints>

## 부록 A. 이 메타 프롬프트가 만들어낼 PRD의 예상 산출물 체크리스트

PRD를 받은 뒤 아래 항목이 빠짐없이 채워졌는지 검증할 때 사용합니다.

- [ ] KPI가 측정 가능한 숫자/기준으로 정의되어 있는가
- [ ] Notion 동기화 방식(Webhook/Polling/수동)의 MVP 권장안과 근거가 있는가
- [ ] PDF 생성 방식 비교표와 MVP 권장안이 있는가
- [ ] 공개 링크의 보안 모델(토큰 길이, 만료 정책)이 언급되어 있는가
- [ ] In Scope / Out of Scope 표가 명확히 분리되어 있는가
- [ ] 기존 라우트 그룹(`(marketing)`/`(auth)`/`(dashboard)`)과의 배치 관계가 설명되어 있는가
- [ ] Open Questions가 실제 의사결정이 필요한 항목으로 구체적인가(막연한 질문 아님)
