# Claude 명령어: Code Review

Next.js 16 + React 19 + TypeScript(strict) 프로젝트 기준으로 코드를 5개 관점에서 단계별로 리뷰합니다.

## 사용법

```
/review:code                        # 인자 없으면 git diff(작업 중인 변경사항) 리뷰
/review:code app/(auth)/login/page.tsx   # 특정 파일/경로 전체 리뷰
```

## 대상 결정 프로세스

1. `$ARGUMENTS`가 비어있지 않으면: 해당 경로를 Read로 전체 읽어서 리뷰 대상으로 삼는다.
2. `$ARGUMENTS`가 비어있으면:
   - `git diff HEAD`로 unstaged + staged 변경사항을 확인
   - 변경사항이 없으면 `git diff HEAD~1`로 최근 커밋 하나를 대상으로 폴백하고, 그 사실을 사용자에게 알린다.
3. 대상 파일이 `.tsx`/`.ts`가 아니면(`.json`, `.md`, 설정 파일 등) 해당 파일은 리뷰 대상에서 제외하고 이유를 짧게 언급한다.

## 리뷰 프로세스 (5단계, 순서대로)

### 1단계 — 버그 및 예외 처리
- 런타임 오류 가능성: null/undefined 접근, 배열 빈 값, 옵셔널 체이닝 누락
- 비동기 처리: `try/catch`에서 `catch (err)` 변수를 실제로 사용하는지, 에러를 무시하고 있지 않은지
- React 19 / Next.js 16 특이사항: Server/Client Component 경계에서 훅이나 브라우저 API를 서버 컴포넌트에 쓰고 있지 않은지, `"use client"` 누락·과다 여부
- 폼: react-hook-form 사용 시 Zod 스키마와 실제 필드가 어긋나지 않는지 (`lib/validations/auth.ts` 패턴 참고)
- 엣지 케이스: 로딩/에러/빈 상태(empty state) 분기가 빠짐없이 있는지

### 2단계 — 성능 및 최적화
- 불필요한 재계산/재렌더링 여부. **주의**: 이 프로젝트는 현재 `useMemo`/`useCallback`/`React.memo`를 전혀 쓰지 않는 단순한 상태이므로, 없다고 무조건 지적하지 말고 실제로 무거운 연산이나 큰 리스트 렌더링이 있을 때만 메모이제이션을 제안한다. 메모이제이션 남용(모든 함수에 습관적으로 useCallback을 붙이는 것)도 동일한 문제로 지적한다.
- Server Component로 남길 수 있는데 불필요하게 `"use client"`가 붙어 클라이언트 번들이 커지는 경우
- 이미지/아이콘: lucide-react 아이콘을 개별 import 하고 있는지(배럴 임포트로 전체 번들을 끌어오지 않는지)
- 리스트 렌더링 시 `key` prop이 index가 아닌 안정적인 값을 쓰는지

### 3단계 — 가독성 및 유지보수성
- 네이밍: 변수/함수는 영어, 의미가 드러나는 이름인지 (CLAUDE.md 컨벤션)
- 중복 코드: `components/ui/`, `components/patterns/`, `components/layouts/`에 이미 존재하는 컴포넌트·유틸을 재구현하고 있지 않은지 먼저 확인
- 컴포넌트 분리: 하나의 파일이 여러 책임(데이터 페칭 + UI + 상태 관리)을 동시에 갖고 있으면 분리 제안
- 매직 넘버/문자열: 반복되는 값이 상수화되어 있는지

### 4단계 — 보안 취약점
- 입력 검증: **클라이언트 측 Zod 검증만 있고 서버 측 재검증이 없는 경우 반드시 지적** (이 프로젝트의 auth 페이지들이 이미 이 패턴을 갖고 있음 — 새 코드가 동일한 함정을 반복하지 않는지 확인)
- 하드코딩된 자격 증명/토큰/API 키 (데모 계정 `demo@example.com`처럼 프로덕션에 남으면 안 되는 값)
- 에러 메시지에 내부 구현 세부사항(스택 트레이스, 원본 `error.message`)을 사용자에게 그대로 노출하는지 (`app/error.tsx` 패턴 참고)
- XSS 가능성: `dangerouslySetInnerHTML` 사용 여부, 사용자 입력을 그대로 렌더링하는 곳
- 외부 링크: `target="_blank"` 사용 시 `rel="noopener noreferrer"` 누락

### 5단계 — 리뷰 리포트 작성
아래 형식으로 **리포트만 출력**한다. 실제 파일은 수정하지 않는다.

```
## 코드 리뷰: <대상 파일/범위>

### 🐛 버그 및 예외 처리
- [심각도: 상/중/하] <파일>:<라인> — <문제 설명>
  → 제안: <수정 방향 한 줄>

### ⚡ 성능 및 최적화
(위와 동일한 형식, 없으면 "특이사항 없음")

### 📖 가독성 및 유지보수성
(위와 동일한 형식)

### 🔒 보안 취약점
(위와 동일한 형식)

### ✨ 개선 코드 예시
가장 우선순위 높은 1~2개 이슈에 대해서만 Before/After 코드 블록으로 제시.
전체 리팩토링 코드가 아니라 **문제가 된 부분 중심의 최소 diff**로 보여준다.
```

## 규칙

- 발견되지 않은 카테고리는 억지로 문제를 만들어내지 말고 "특이사항 없음"으로 표기한다.
- 심각도가 낮은 스타일 지적보다 실제 버그/보안 이슈를 우선 배치한다.
- 리포트 출력 후, 사용자가 반영을 원하면 그때 Edit으로 진행한다 — 이 명령어 자체는 파일을 수정하지 않는다.
- 프로젝트 컨벤션(CLAUDE.md, AGENTS.md)과 충돌하는 제안은 하지 않는다.
